## 3. 上线前必须

### R1 任何已开具发票都不可改方向

**现状**

方向在两处编辑契约里都还在：`shared/api.interface.ts` 的 `UpdateInvoiceDto.direction`，以及 `finance.dto.ts` 的同名字段。`updateInvoice` 用**修改后**的方向决定是否重建凭证。

- 进项改为销项：`rebuildVoucher=false`，旧进项凭证不作废。
- 销项改为进项：可能新建进项凭证，且不校验供应商。
- 旧凭证已过账时 `decideInvoiceEdit` 会拒绝。草稿或没有凭证时会留下错账。

`InvoiceEditDialog` 目前不提交方向。漏洞在契约和 API。禁止修改必须落在“已开具发票的更新接口不接受该字段”，不能只改 `shouldRebuildInvoiceVoucher`。

**做法**

1. 从 `shared/api.interface.ts` 的 `UpdateInvoiceDto` 删除 `direction`。类 DTO 同步删除。创建 DTO 保留方向。
2. 已开具发票的 PATCH 若仍带 `direction`，由 `forbidNonWhitelisted` 返回 400。服务层再挡一次：请求体含该键即 400，文案为须作废后重开。不要改成“方向相同就放过”。
3. 前端编辑保存的请求体不得再包含 `direction`。现有编辑弹窗没有该字段，收口时搜一遍调用 `updateInvoice` 的地方。
4. 历史只出清单，不自动改账。用下面两条 SQL，结果交财务处理。

销项发票却挂着未作废的发票来源凭证（方案 A 下销项开票不生成凭证）：

```sql
SELECT i.id, i.code, i.invoice_no, i.direction, i.status,
       v.id AS voucher_id, v.code AS voucher_code, v.status AS voucher_status
FROM erp_invoice i
JOIN fin_voucher v
  ON v.source_type = 'invoice'
 AND v.source_ref = 'invoice:' || COALESCE(i.invoice_no, i.code)
 AND COALESCE(v.status, '') <> 'voided'
WHERE COALESCE(i.direction, 'sales') = 'sales'
  AND COALESCE(i.status, '') <> 'voided';
```

进项发票的未作废凭证里出现销项科目 `6001` 或 `222101`（`outputIssueLines` 的贷方），或销项发票的未作废凭证里出现进项科目 `222102`（`inputIssueLines` 的借方）。这三个编码在当前科目表里就是末级，`fin_voucher_line.account_code` 存的就是它们，不要再往下拆叶子：

```sql
SELECT i.id, i.code, i.invoice_no, i.direction,
       v.id AS voucher_id, v.code AS voucher_code,
       l.account_code, l.debit, l.credit
FROM erp_invoice i
JOIN fin_voucher v
  ON v.source_type = 'invoice'
 AND v.source_ref = 'invoice:' || COALESCE(i.invoice_no, i.code)
 AND COALESCE(v.status, '') <> 'voided'
JOIN fin_voucher_line l ON l.voucher_id = v.id
WHERE COALESCE(i.status, '') <> 'voided'
  AND (
    (COALESCE(i.direction, 'sales') = 'purchase' AND l.account_code IN ('6001', '222101'))
    OR
    (COALESCE(i.direction, 'sales') = 'sales' AND l.account_code = '222102')
  );
```

**验收**

- `UpdateInvoiceDto`（shared 与 class）都没有 `direction`。
- 前端保存已开具发票的请求体没有该字段；手工 PATCH 带上该字段得到 400，发票行与未作废凭证不变。
- 不带方向的备注、关联应收编辑保持现有守卫。销项编辑仍不生成销项凭证（`invoice-edit-guard.spec.ts`）。
- 上面两条 SQL 有执行结果。有行则只列入清单，不写修复脚本。

### R2 多主体下新凭证必须归到我方主体

**现状**

解析顺序见 `tax-entity-resolver.ts`：显式值 → 合同 → `lookupBySourceType` → 第 ③ 级。第 ③ 级的 SQL 是：

```sql
SELECT id FROM md_tax_entity
WHERE is_default = 1 AND status = 'active'
```

它数的是**默认主体**，不是启用主体。主体 A `is_default = 1`、主体 B `is_default = 0` 且都 `active` 时，启用主体已有 2 个，`candidates.length === 1`，resolver 仍返回 A。只给四类凭证加 lookup、不改这一级，无法推导的单据仍会被默认主体静默填上。

`lookupBySourceType` 只有 `cost` / `revenue` / `invoice`。折旧、报销、采购退货、销售退货没有分支，调用点也没传显式主体。`ast_asset`、`fin_expense_apply`、`fin_expense_claim` 都没有 `tax_entity_id`。`CreateAssetDto`、`CreateExpenseApplyDto`、`CreateExpenseClaimDto`（shared 与对应 class DTO）都没有该字段。建卡弹窗是 `AssetCreateDialog`，费用弹窗是 `CreateExpenseApplyDialog`、`CreateExpenseClaimDialog`。资产模块没有更新资产的 PATCH。

**主体从哪来**

“单主体”指 `status = 'active'` 的行数等于 1。“多主体”指该计数大于 1。不要用 `is_default = 1` 的行数代替这个判断。

| 单据 | 单主体 | 多主体 |
|---|---|---|
| 费用申请 / 报销，有 `project_id` | 项目 → 合同的 `tax_entity_id`；合同没有主体时，用那一个启用主体 | 必须用项目 → 合同的 `tax_entity_id`。合同没有主体则创建 400 |
| 费用申请 / 报销，无项目 | 主体可空，出凭证时用那一个启用主体 | 单据上的 `tax_entity_id` **必填**，否则创建 400 |
| 资产，有项目且合同有主体 | 折旧用合同主体，资产自身主体不参与 | 同左 |
| 资产，有项目但合同没有主体 | 用资产自身 `tax_entity_id`；为空则用那一个启用主体 | 资产自身主体必填，仍为空才 400。不要因为合同没主体就拒绝已填写的资产主体 |
| 资产，无项目 | 资产主体可空，折旧用那一个启用主体 | 资产自身主体必填，否则建卡 400 |
| 采购退货 | 订单合同、项目合同，仍没有则用那一个启用主体；供应商上的我方主体只作已填写的最后候选项 | 顺序相同，但没有唯一启用主体可兜底。合同与 `md_supplier.tax_entity_id` 都为空则拒绝生成 `purchase_return` 凭证 |
| 销售退货 | `sales_return.contract_id` 或收入单 `erp_project_revenue.contract_id` 的主体；没有则用那一个启用主体 | 必须从这两处之一得到主体，否则拒绝生成 `sales_return` 凭证 |

`md_supplier.tax_entity_id` 是我方归属列，不是对方税号。只允许作为采购链路上已填写的最后候选项，优先级低于订单合同和项目合同。为空时不得生成凭证。

**做法**

1. 本需求**只改** `expense`、`depreciation`、`purchase_return`、`sales_return` 的归属。`cost`、`revenue`、`invoice` 保留今天的第 ③ 级（`is_default = 1 AND status = 'active'` 恰好一行则用它）。这是已上线口径，不在本次范围，也不要把文末原则理解成这三类也要改。
   - 新四类：先数 `status = 'active'`。等于 1 时，前面各级都没命中才用这一个启用主体。大于 1 时不再执行默认主体那条 SQL，解析不到就拒绝出凭证，禁止用默认主体填这四类的缺口。等于 0 时返回 `null` 并拒绝出凭证。
2. `ast_asset`、`fin_expense_apply`、`fin_expense_claim` 增加可空 `tax_entity_id`（迁移幂等）。列保持可空，避免单主体历史行迁不进去。多主体必填放在服务层。
3. 同一批改动接入写入和回显，否则规则上线后用户没有地方填，也看不到已选值：
   - shared 与 class：`CreateAssetDto`、`CreateExpenseApplyDto`、`CreateExpenseClaimDto` 增加可选 `taxEntityId`（UUID）。
   - 响应同时增加：`AssetItem`、`ExpenseApplyItem`、`ExpenseClaimItem` 增加 `taxEntityId: string | null`。列表、创建成功、详情都返回它，供弹窗回显。
   - `AssetCreateDialog`、`CreateExpenseApplyDialog`、`CreateExpenseClaimDialog` 增加纳税主体选择。多主体下：报销无项目、或资产无项目、或资产有项目但合同没有主体时，前端把主体标为必填，空提交由后端 400。合同已经有主体时，资产主体可以不填，折旧用合同主体。
   - 资产目前不能 PATCH。建卡时就要能写入主体；另加一个只改 `taxEntityId` 的接口，供盘点后补历史卡片，权限与建卡相同。补录成功后的 `AssetItem` 带回新值。
4. 报销关联申请时带出申请上的主体，允许在报销单上改，凭证以报销单为准并显式传入。
5. `lookupBySourceType` 增加 `expense`、`purchase_return`、`sales_return`。折旧的 `sourceRef` 是 `depreciation:{期间}:{科目}:{批次}`，含多个冒号。计提时把已解析的 `taxEntityId` 显式传给 `generateVoucherDraft`，不要用第一个冒号后的整段去查。
   报销作废的 `sourceType` 仍是 `expense`，`sourceRef` 为 `expense-void:{原单号}`，整段里只有这一个冒号。`slice(indexOf(':') + 1)` 得到的就是原单号，不会变成 `void:{原单号}`。不要为了这句话去改成“取最后一个冒号”。真正要补的是查询条件：按该原单号查 `fin_expense_claim` 时，`status = voided` 也必须返回主体（单据上的 `tax_entity_id`，没有则用其项目合同主体）。若 lookup 只保留未作废单据，红字凭证在多主体下会被拒绝，补偿队列也补不出来。采购退货、销售退货的红冲同样按原单号查，不按“当前未作废”过滤。
6. 上述四类在多主体下解析仍为 `null` 时，不插入凭证，补偿原因写“未归属纳税主体”。`cost` / `revenue` / `invoice` 仍可按旧兜底落默认主体。
7. 上线前跑完下面的盘点。有行则先补主体，不写自动归集。


### R3 项目基线在创建时占用（策略 A）

**现状**

| 闸门 | 创建时看什么 | 超限 | 锁 |
|---|---|---|---|
| 费用预算 `checkBudget` | 费用申请与报销的占用/已执行 | 申请 400；报销改为 `escalated` | 无 |
| 项目基线 `assertProjectBaseline` | 只加总 `erp_project_cost` | 400 | 无。审批插入成本时（约 879 行）不再复算 |

成本要到审批才写入。两笔创建可以同时看到同一个成本合计。本文不再把“创建放行、审批拒绝”和“创建即互斥”写在一起。

**选定策略：创建即占用。** 不采用“允许在途超占、只在审批拒绝”。

占用公式（同一 `project_id`）：

```text
已归集 = Σ erp_project_cost.amount
         （红冲负数行自然抵消，不要把已红冲的原行再加绝对值）

在途报销 = Σ fin_expense_claim.amount
           WHERE status IN ('pending', 'escalated')
           （approved 已经写入成本，不要再加，避免与已归集双计）

在途申请 = Σ fin_expense_apply.amount
           WHERE status IN ('pending', 'approved')
             AND 不存在引用它的报销
                 （fin_expense_claim.apply_id = 申请.id
                  AND claim.status NOT IN ('rejected', 'voided')）

项目占用 = 已归集 + 在途报销 + 在途申请
```

去重：报销 `applyId` 指向仍有效的申请时，只计报销，不计申请。没有报销的申请仍计申请。

当前单据还没落库或仍挂在在途里，必须先从合计里拿掉，否则会把自己算两次：

```text
创建申请：占用不含本次申请。比较的是“其他占用 + 本次金额”
创建报销：占用不含本次报销。若 dto.applyId 指向仍计入在途申请的那张申请，先去掉该申请，再加本次报销金额
审批报销：当前 claim 仍是 pending 或 escalated，先从在途报销去掉它，再比较“已归集 + 其他在途 + 本次成本”
```

例：申请 6 万已批准、尚未报销，预算 10 万。按该申请创建报销 6 万时，先排除这张申请的 6 万，占用按本次 6 万计，创建成功。若创建时不排除，会看成 12 万并误 400。审批这张 6 万时，在途里已经有它自己，先排除再插入成本，不能把 6 万再加一次。

`checkBudget`（`budget-check.ts`）今天在创建申请和创建报销时都会调用。申请的 `pending` 与 `approved` 全部计入占用，报销的 `pending` 与 `escalated` 也计入占用。因此“已批准申请 6 万 + 据此报销 6 万”在软预算里也会被加成 12 万，报销被标成 `escalated`。项目基线排除了当前单据之后，这条线仍会双计。

`checkBudget` 与项目基线使用同一套排除，在调用前从入参里拿掉，不要只锁 `fin_budget` 行：

```text
创建申请：本次金额只作为 docAmount。occupied 不含本次申请（创建时尚未插入；若先插入再查，按 id 排除）
创建报销：occupied 不含本次报销；若 dto.applyId 指向仍在占用中的申请，从申请占用里拿掉该申请，再只加本次报销金额
审批报销：今天的审批路径不调用 checkBudget。若审批要复算软预算，先按 id 排除当前 claim，再算其他占用 + 本次金额
```

`budget-commitment.service.ts` 是预算三算报表（合同、采购订单、已批准申请），不是项目基线，也不是 `checkBudget`。不要用它的口径替换这两处公式。

**做法**

1. 创建费用申请、创建报销、审批通过报销，凡带 `project_id`，都在同一事务里先 `SELECT erp_project WHERE id = ? FOR UPDATE`，再按公式和上面的排除规则重算。其他占用加上本次金额后大于 `erp_project.budget` 则 400，不插入。排除必须发生在查询结果上：传给 `computeBudgetCheck` 的申请行去掉 `dto.applyId`，报销行去掉当前 claim id。只在需求文字里写“排除”而不改这两份入参，软预算仍会双计。
2. 审批仍要复算，并且排除当前 claim。排除和比较都要在 `INSERT erp_project_cost` 之前做完。若先插入成本再排除当前 claim，这张单的金额会留在已归集里，排除之后反而少算。排除自身后若仍超限，审批 400，且不插入这条成本。两笔各 6 万、预算 10 万，第二笔在**创建**失败。审批复算只防创建之后的增量。
3. 费用预算策略不变：申请超限 400，报销超限 `escalated`。判断超限之前先按上一段从 `checkBudget` 的占用入参里排除当前单据。不要把项目基线改成升级，也不要把报销软预算改成拒绝。
4. 同一事务里还要锁费用预算行时，顺序固定为：先 `erp_project`，再 `fin_budget`。命中多行预算时按 `fin_budget.id` 升序依次 `FOR UPDATE`。没有项目的单据只按 id 顺序锁预算行。
5. 报销作废后，该单不再进入在途报销；已插入的负数成本进入已归集。作废后同等金额可以再次创建。

**验收**

预算 10 万、已归集 0、无其他在途：

- 两笔各 8 万并发创建：至多一笔成功，另一笔 400。
- 先创建 6 万成功；再创建 6 万返回 400。不存在“两笔都创建成功、第二笔审批才 400”。
- 第一笔 6 万审批通过并写入成本后，再创建 5 万返回 400（已归集 6 万 + 本次 5 万）。
- 已批准申请 6 万、费用预算与项目预算都至少 10 万、尚未报销：据此创建报销 6 万成功，状态是 `pending` 而不是 `escalated`（项目基线和 `checkBudget` 都先排除该申请）。在只有这张 6 万在途时，再创建无申请的 5 万，项目基线 400；再创建 4 万成功。
- 审批一笔已创建的 6 万：在途里已含这张单时仍能通过，并只插入一笔 6 万成本。预算只剩 6 万、另有其他在途 2 万时，这张 6 万审批 400。
- 费用预算超限的报销仍是 `escalated`。费用申请超限仍是 400；两笔并发申请合计超费用预算时至少一笔 400。
- 作废已创建、未审批的 8 万后，可以再创建 8 万。

## 4. 第一批迭代

### R4 供应商银行账号按能力返回

事实：没有单独的供应商详情接口。明文出现在 `GET /api/master-data/suppliers`（`mapSupplier`）、列表页「银行账户」列，以及 `SUPPLIER_EXPORT_COLUMNS` 导出的 `供应商列表.xlsx`。列表走 crm 读兜底，项目经理有 `crm: r`。

`bankAccount` 只在调用方具备 `finance` 读能力时返回原文，否则 JSON 与导出都是空字符串。列表仍对 crm 读开放，名称和联系人保持可见。`project_manager` 拉取列表并导出，两处都没有账号明文；`finance_viewer` 两处都能看到。

### R5 首页按能力请求

`/` 渲染 `DashboardPage`，进页就请求挂了 `@FinanceRead()` 的概览、毛利、贡献、趋势、税、账龄，以及 `@HrRead()` 的人力概览。人事和账号管理员会 403。

不要放宽 `FinanceRead` / `HrRead`。首页用 `hasCapability` 决定请求哪些块。一块能力都没有时显示通用空态。`finance_viewer` 仍看到财务块。

### R6 附件下载复用单据权限

`files.service.open` 只放行文件 `ownerUserId` 或 admin。附件列表已经有 `ResourceAclService.assertCanAccess`：按 `resourceType` 区分项目可见、`finance_viewer`、`hr_manager`、行政仅 admin。下载没有走这层，所以财务能看发票附件记录，但打开文件 403。

不要把下载改成登录即可，也不要另写一套映射。`comp_attachment.file_url` 能对应到该 `comp_stored_file` 时，对每一条引用调用现有 `assertCanAccess`；**任一引用通过即可下载**（并集）。没有任何附件引用时，维持 owner 或 admin。`ownerUserId` 为空且无附件引用的历史文件仍仅 admin。

### R7 生产入口不要用纯 HTTP 暴露 3000

`docker-compose.yml` 当前是 `3000:3000`，容器 `NODE_ENV=production`，Cookie 默认 Secure。纯 HTTP 下登录响应成功，浏览器不保存会话。

生产改为 `127.0.0.1:3000:3000`，由 HTTPS 反代对外。`COOKIE_SECURE=false` 只允许本地 HTTP。`.env.example` 与 `docs/RUNBOOK.md` 写明这一条。

### R8 报销作废凭证的 dead 要看得见

作废事务先提交状态、应付作废和负数成本，红字凭证在事务外生成，失败进补偿队列。队列每 10 分钟重试，不是无人处理。本项接受重试成功前的账差，不要求改成同一事务。

`retryPendingJobs` 现在只返回 `retried` / `dead` 两个计数。返回值要带上 dead 条目的 `sourceRef` 列表（`expense-void:{单号}`），运行记录和日志都用这份列表。不要只多打一条没有单号的日志。管理端能看出待重试条数和 dead 条数。重试成功后存在该 `sourceRef` 的凭证，分录为借 `2202`、贷 `6602`。

### R9 草稿合同在提交前提示金额差

不阻断上线，也不在逐条加明细时阻断录入。明细只能草稿改，生效后头表金额锁定。现在不一致可以留到提交/审批的 `assertItemSum`。

若“每次保存明细都与头表差 0.01 即 400”，头表仍为 0 时第一条 10 万明细就无法保存。本项改成：

- 草稿新增、修改、删除明细：允许保存，不返回 400。`create` / `update` 今天返回 `ContractItemView`，`remove` 返回空。改为信封，不要把差额塞进明细字段里：
  - 新增、修改：`{ item: ContractItemView, headerAmount, itemSum, differs }`
  - 删除：`{ headerAmount, itemSum, differs }`
  - `list` 仍返回 `ContractItemView[]`
  前端用 `differs` 作警告。
- 草稿修改头表 `amount`，且已经有明细：相差超过 0.01 则 400，文案写出两个数。头表还没有明细时允许先写金额。
- 提交和审批保持现有 `assertItemSum` 硬校验。

不要求保存明细时自动改头表金额。

### R10 逐个创建类弹窗核对双击

不要用 `isSubmitting` 的出现次数判断全站。列出创建应收、应付、付款、成本、报销、发票、合同、项目的弹窗。每个确认：请求未返回前提交按钮 `disabled`，且后端对同一业务键的第二次插入会冲突。缺按钮保护的补局部 `saving`。已经 `disabled={saving\|submitting\|busy}` 的记通过，不改。
