## 六、P0：上线前必须修复

### P0-1 编辑销项发票会生成一张本不该存在的销项凭证 → 收入/销项税/应收三重重复入账

**证据（静态，已回源）**

- `server/modules/finance/invoice.service.ts:405`：方案 A 明确"收入确认为准，**销项开票只登记台账，不再生成收入/税凭证**"。
- 同一文件 `:752-910` 的 `updateInvoice`：只要改动 `amount/taxRate/invoiceDate/contractId/...`（`affecting.length > 0`），就会走 `decision.rebuildVoucher`。
- `server/modules/finance/invoice-edit-guard.ts:109`：凭证状态为 `null` 时返回 `{ ok: true, rebuildVoucher: true }`。该 `null` 既可能是"进项票尚未生成凭证"，也可能是"销项票按方案 A 本来就没有凭证"——守卫没有区分方向。
- `invoice.service.ts:903-910`：`isPurchaseRow ? inputIssueLines : outputIssueLines`，对 sales 也出 `outputIssueLines`，并 `generateVoucherDraft({ sourceType:'invoice', sourceRef:'invoice:<票号>' })`。

**影响（举例）**

收入确认 106,000（含税 6%）时已生成：

```
借 1122 应收账款 106,000
  贷 6001 主营业务收入 100,000
  贷 222101 应交增值税（销项）6,000
```

随后登记一张 106,000 的销项发票（按方案 A 不出凭证）。有人修正开票日期或金额，触发 PATCH：

```
再生成一张同额凭证：
借 1122 106,000 / 贷 6001 100,000 / 贷 222101 6,000
```

结果：6001 由 100,000 变 200,000，222101 由 6,000 变 12,000，1122 虚增 106,000；**借贷仍然平衡、逐张凭证看起来都对**，只有利润表/增值税底稿对不上。

**修复（最小改动）**

1. `updateInvoice` 的重建分支加方向白名单：**只有 `direction === 'purchase'` 才允许重建**；销项一律不重建（与 `createSalesInvoice` 的方案 A 一致）。
2. 若需兼容历史上"销项票曾出过凭证"的数据，改为"仅当已存在同 `sourceRef` 的非 voided 凭证时才作废重建"，**绝不从 0 新建**。
3. 把 `invoice-edit-guard.spec.ts` 里"无凭证 → 重建"的断言按方向拆成两组；当前这条测试**把 bug 钉成了契约**。

**验证状态**：静态确认；建议补一条 `direction='sales' + voucherStatus=null + amount 变更 → 不产生新凭证` 的集成测试。

### P0-2 报销单作废不红冲凭证、不冲回项目成本

**证据**

`server/modules/fin-expense/fin-expense.service.ts:741-757`：

```ts
// action === 'void'
await this.db.transaction(async (tx) => {
  await tx.update(finExpenseClaim).set({ status: 'voided', ... });
  if (ap) {
    await tx.update(erpApBill).set({ status: 'voided', ... });
  }
});
```

同一 service 的审批通过分支：

- `:824` 写入 `erp_project_cost`（`sourceRef: expense:<单号>`）；
- `:845` 生成凭证 `借 6602 管理费用 / 贷 2202 应付账款`。

作废分支**没有**调用 `ApService.voidAp`（后者的 `ap-void` 红字分录在 `ap.service.ts:355`），也**没有**冲回项目成本。

**影响（举例）**

差旅报销 8,000 审批通过：6602 借 8,000、2202 贷 8,000、项目成本 8,000。

作废后：

- 应付台账查不到该单（status=voided）；
- 总账 2202 仍挂 8,000 贷方，形成"无对应应付单的应付"；
- 费用 6602 与项目成本各虚增 8,000 → 利润虚减、项目毛利永久偏低；
- 凭证补偿队列不覆盖此类（根本没有生成红字）。

**修复**

作废事务内：

1. 复用 `ApService.voidAp` 的等价逻辑（同事务生成 `ap-void` 红字）；
2. 插入负数 `erp_project_cost`（`offsetOf` 原行 / 或标记原行已冲回）；
3. 若 `voidAp` 返回失败，抛错回滚，不能"业务已作废、凭证没生成"。

**验证状态**：静态确认；`ExpenseClaimPanel` 已暴露 `void` 动作（`shared/api.interface.ts` 的 `ExpenseClaimAction` 含 `void`），可端到端复现。

### P0-4 新装首登三重阻断：bootstrap 口令不达策略 + MFA 无绑定入口 + 前端无 MFA/改密页面

这是三个独立缺陷叠加成"新装系统没有可用管理员"的发布阻断。

**(a) bootstrap 口令不达代码强制的 12 位策略**

- `auth.service.ts:69-90`：`onModuleInit` 在 `sys_user` 为空时调用 `validatePassword`；`DEFAULT_PASSWORD_POLICY.minLength = 12`（`login-security.service.ts:28`）。
- 仓库文档/`.env` 中的 bootstrap 口令 `Cs.******（9 位）` 只有 **9 位** → `validatePassword` 失败 → `onModuleInit` 抛错；生产 `abortOnError: true`（`main.ts`）→ 进程启动失败，**一个管理员也建不出来**。
- 同期 `set-admin-creds.mjs` 只要求 8 位，`identity.createUser/resetPassword` 也只要求 8 位，与 12 位策略不一致。

**(b) 强制 MFA 与首登互锁**

- `login-security.service.ts:283-287`：`requiresMfa` 对 `admin / user_admin / finance_viewer` 恒为 true。
- `auth.service.ts:208-220`：密码正确后，若 `enabled=false && required=true`，直接抛 `UnauthorizedException('请先在设置页完成 MFA 绑定后再登录')`，**不签发任何会话**。
- 唯一绑定入口 `POST /api/auth/mfa/setup` 需要已登录；且它没有能力注解，被兜底为 `dashboard` 写权限（仅 admin），普通用户即使有会话也进不去。
- 当前 dev 管理员能登录，是因为数据库里 `mfa_required_override = 0`（人工改库的 workaround）；**新装库没有这一行**。

**(c) 前端没有 MFA / 改密入口**

- `client/src` 全量 grep：`mfaRequired` / `mfa/verify` / `mfa/setup` / `password/change` **0 命中**。
- `LoginPage.tsx:72-92` 只判断 HTTP 200/401/403/429；若后端返回 `{ mfaRequired: true }`（200），它会直接 `goAfterLogin()` 整页跳 `/`，而 `/` 的守卫看到无会话又弹回 `/login` —— **MFA 已启用用户的登录循环**。
- 飞书回调命中 MFA 时会 302 到 `/login?mfa_required=1&mfa_token=...`（`auth.controller.ts:366-368`），前端同样没有处理。

**修复**

1. bootstrap 口令改为 ≥12 位、四类字符，并在启动日志里明确"已创建初始管理员"；或在 `onModuleInit` 里对 bootstrap 账号写 `mfa_required_override=0`，强制首登后绑定。
2. 对"required 且未绑定"的用户签发**仅能 setup/confirm 的一次性会话**，而不是拒绝；或允许登录但强制跳转绑定。
3. `mfa/setup` 对任意登录用户开放（仅作用于本人），并在前端补：
   - 登录第二步（`mfaRequired` → 6 位 TOTP）；
   - 设置页 MFA 绑定/恢复码/关闭；
   - 修改密码页。
4. 补一条端到端测试：新装库 → bootstrap → 首登 → 绑定 MFA → 重新登录。

### P0-5 `user_admin` 可重置超管密码 / 改角色 / 禁账号，账号管理员可越权接管

**证据**

- `shared/rbac.ts`：`identity: { admin:'rw', user_admin:'rw' }`。
- `identity.controller.ts:119` 类级 `@CanCapability('identity')`，因此 `user_admin` 可调用该 controller 全部方法。
- `identity.service.ts:255` `resetPassword(actor: { userId: string }, id, password?)`：**只收 userId，不校验 actor 角色，也不校验目标是否 admin**。它会把目标密码改成调用方指定的值（或返回随机临时密码），并 `sessions.revokeUser(id)`。
- `identity.service.ts:449` `sanitizeRoles`：只拦"非 admin 授予 admin"，**允许 `user_admin` 给自己/他人授予 `hr_manager`、`finance_viewer`、`project_manager`**。
- `identity.service.ts:209` `setStatus`：只保护"最后一个 admin"，`user_admin` 可以禁用其他 admin（包括非最后一个超管）。

**影响**

`user_admin` 是"账号管理员"角色，按最小权限不应能接管超管。当前路径：

1. `POST /api/identity/users/<adminId>/reset-password` → 得到/设置 admin 新密码；
2. 用新密码登录 → 获得 `admin` 全部能力；
3. 或 `PUT /api/identity/users/<自己的id>/roles` 自授 `hr_manager`，直接读写工资/员工。

**修复**

1. 在 `resetPassword / setStatus / setRoles / updateUser` 中，若目标用户含 `admin` 而 actor 不含 `admin` → 403；
2. 禁止修改自己的角色集；
3. `sanitizeRoles` 只允许授予 actor 自己拥有的角色（admin 例外），或把角色管理收窄为仅 admin；
4. 所有身份变更写审计并撤销目标会话（见 P1-4）。

收入 106,000（6%）且已全额开票 106,000 → `invoicedNet=100,000` → 未开票收入 = **6,000**（应为 0）→ 第 1 行销售额 100,000+6,000=106,000（应 100,000），且每月必报 `unbilled_revenue_tax_pending`，噪声淹没真实差异。

另 `:665-670` 小规模免征额度用 `invoice.salesNet`（只含已开票）判定，第 1 行却含未开票 → **存在**把"开票 90,000 + 未开票 30,000"判成"额度内"而免征两项附加税的风险（后半段为静态推导，需按申报口径复核）。

**修复**

1. 两处统一为不含税：`revenueNet = sum(amount*100/(100+税率))`（与 `return.service.ts:832` 同式），或用记录税率逐笔 `splitTax(...).net` 求和；
2. 免征判定传入 `totalSalesNet`；
3. 补"全额开票 → 未开票收入 = 0"的单测。

### P1-9 个税累计减除费用按"自然月序号"而非"本单位任职月份数"

**证据**

- `hr-pay.service.ts:195`：`const monthIndex = Number(dto.period.slice(5, 7));`
- `payroll-engine.ts:276`：`ytdBasicDeduction = 5000 × monthIndex`。
- `md_employee.hire_date` 存在，但工资链路从未读取（`grep hireDate` 仅命中 hr-core / hr-self-service）。

**影响（举例）**

7 月入职、月薪 10,000：

- 正确：累计减除 5,000×1；累计应税 10,000−5,000=5,000；预扣 150；
- 系统：5,000×7=35,000；累计应税 0；预扣 0。

每月少扣 150，至 12 月少扣约 900，只能年度汇算补 → 单位代扣代缴申报错误（国税总局公告 2018 年第 61 号）。

**修复**

`monthIndex` 改为 `max(1, 当前月 − 入职月 + 1)`（跨年入职取自然月），并把"实际计税月份数"落到 `ytd_basic_deduction` 便于复核。

## 十、专题：权限模型回归（为什么"UI 能进、接口 403"）

### 10.1 角色→能力矩阵（`shared/rbac.ts`）

| 角色 | dashboard | finance | crm | projects | hr | identity | drive | settings_appearance |
|---|---|---|---|---|---|---|---|---|
| admin | rw | rw | rw | rw | rw | rw | rw | rw |
| finance_viewer | r | **r** | r | — | — | — | r | r |
| project_manager | r | — | r | **rw** | — | — | r | r |
| hr_manager | r | — | — | — | **rw** | — | r | r |
| user_admin | r | — | — | — | r | **rw** | r | r |
| drive_editor | r | — | — | — | — | — | **rw** | r |

### 10.2 实际结果（静态 + 实测）

| 角色 | 预期 | 实际 |
|---|---|---|
| `finance_viewer` | 读财务报表/账簿/银行流水/导出 | **全部 403**（25+8+2 个 GET 用了 `@CanCapability('finance')`） |
| `project_manager` | 只看/改自己项目 | 列表收窄，但 **PATCH 任意项目 / 写任意项目成本收入** 均可；工时/附件/用户姓名 403 |
| `hr_manager` | HR 读写 + 首页 | 首页财务块 403；待办 403；附件/工时/补卡 403；工资可写 |
| `user_admin` | 账号管理 | 可重置 **admin** 密码、可自授业务角色、可禁其他 admin |
| `drive_editor` | 云盘读写 | 云盘 OK；待办/附件/用户姓名 403 |
| 无角色登录用户 | 看板/待办/个人资料 | 待办 403、用户姓名 403、改密 403；仅 `GET /api/users/search` 等少数可用 |

### 10.3 根因链

```
@CanCapability         → access='rw' → hasWriteCapability（只认 rw）
@CanCapabilityRead     → access='r'  → hasCapability（r/rw 均可）
未注解 + POST          → 兜底 {dashboard,'rw'} → 仅 admin
未注解 + 前缀 write:null → 兜底取 read 能力，但仍是 'rw'
```

两条独立缺陷：

1. **读接口用了写装饰器**（55 处）→ 只读角色被挡；
2. **自助写接口没有注解**（29 处）→ 兜底按域写权限 → 普通用户被挡。

它们叠加，产生"除了 admin，谁都做不了事"的现象。这也解释了为什么 12 个浏览器走查（admin 登录）能全绿。
