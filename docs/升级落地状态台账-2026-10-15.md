⚠️ **教训记录 ②（2026-10-15 新增，同类但更隐蔽）**：**"代码引用了不存在的列"**
是比"表没建"更难发现的一类缺陷 —— 代码看起来完全正确，`typecheck`/`lint` 都过，
但运行时 SQL 直接报 `column ... does not exist`，接口 500。

本次实测发现两处（均已修复）：
- `fin_voucher.tax_entity_id` —— 被 A-01/A-02/A-03/A-06/D-03 共 5 个文件引用，
  列却从未创建。**任何传 `taxEntityId` 的报表请求都 500**，
  也就是说台账此前对 A-01「支持按纳税主体分别出具」的 ✅ 标注是未经验证的。
- `ast_asset.keeper_employee_id` —— `/api/asset/assets/:id/ownership` 调用即 500
  （因前端从未调用该接口而长期潜伏）。

**为什么 CI 没拦住**：`migrate:dryrun` 与迁移链集成测试**只执行 DDL**，
从不执行这些业务查询；而现有集成测试都没传这些参数。
"迁移通过"与"功能可用"之间有一条完全没被覆盖的缝。

**已加的可执行约束**：`server/test/integration/column-reference-audit.spec.ts`
静态扫描全部源码，建立「SQL 别名 → 表」映射后与真实库结构比对，
任何不存在的列即失败（已实测：临时插入 `a.ghost_employee_id` 会立刻报错）。

**验收要求补充**：涉及新列的报表/查询，**必须有一条集成测试真的执行该查询路径**
（含该参数），仅"迁移里有这个列"不算。

⚠️ **教训记录 ③（2026-10-15，测试基础设施）**：**假失败比慢更糟**。

全量跑时 `export-file.spec.ts` 超时失败，但**单跑 27s 通过**。排查结论：
jest 默认 `testTimeout` 为 5000ms，而本仓有多个 pglite 集成规格，每个都要
boot pglite WASM 并跑完整迁移链（**迁移本身只占 1.3s**，实测各条耗时合计；
其余是 WASM 启动与 Drizzle 初始化）。随 pglite 规格增多，worker 争用会把
**与之无关的普通规格**也拖过 5s 而失败 —— 这是资源争用导致的假失败，不是缺陷。

处置：在 `jest.config.cjs` 显式设 `testTimeout: 30000` 并写明原因。
**为什么不给单个规格加 `jest.setTimeout`**：争用影响**任意**规格，逐个加必然漏，
而漏掉的那个会在 CI 上偶发失败，最终让人开始忽略红灯。

**推广的判据**：任何"本地过、CI 偶发失败"的现象，先怀疑**并行资源争用**
而不是代码缺陷；反之，看到红灯也先确认它**可复现**再动手改业务代码。

⚠️ **教训记录 ④（2026-10-15，权限显隐的静默失效）**：**能通过 typecheck 的错误，
才是最危险的那一类**。

B-01 前端收敛时，codemod 把 `route-capability.ts` 里 `write: null` 的规则
（语义是"写能力与 read 相同"，如 `admin_ops` / `pur_asset` / `tax_entity`
在 MATRIX 中**没有** `_write` 变体）误当成"未写 write 字段"，
于是生成了 `admin_ops_write` / `pur_asset_write` / `tax_entity_write`
三个**不存在的能力码**。

后果的严重性在于它是**静默的**：`<CanCapability capability="不存在的码">`
不报错、不告警，只会永远渲染 `fallback` —— 整个管理模块的按钮**永久消失**，
而界面看上去只是"我这次没权限"。

**为什么 `typecheck` 拦不住**：`CanCapability` 的 prop 类型是
`capability: Capability | string`，`| string` 让**任意字符串都合法**，
联合类型被完全绕过。修好它需要把类型收窄为 `Capability`
（属平台层改动，已登记为遗留项），但**不能只依赖类型**。

因此新增 CI 门 `check:rbac:frontend`（`scripts/check-frontend-rbac.mjs`）：
- `<CanCapability>` 的能力码必须存在于 `shared/rbac.ts` 的联合类型（运行时清单核对）；
- `<CanRole>` 必须登记白名单并写明**具体理由**；
- 白名单防腐化（条目指向的文件必须仍存在且仍含 `<CanRole>`）。

**推广的判据**：任何"拼错字符串只会让功能静默消失"的地方
（权限码、字典 key、路由 path、指标 code），都必须有**运行时清单核对**，
不能只靠类型系统 —— 尤其是 prop 类型里出现 `| string` 的时候。
本次这个门**正是在写完当天就抓到了自己 codemod 的这个 bug**。

⚠️ **教训记录 ⑤（2026-10-15，状态标注的粒度）**：**"未做"必须精确到子项。**

C-14 台账原写「绩效/培训深化**未做**」，实测却是**做完了** ——
`hr_appraisal` / `hr_training` / `hr_training_record` 三表齐备，
`hr-pay.controller.ts` 有 `appraisals` / `trainings` 路由，
`client/src/api/hr` 有对应函数，`AppraisalPanel.tsx` / `TrainingPanel.tsx` 存在。
真正未做的是**另一个子项**：①考勤规则（班次与迟到自动判定）。

方向反了的失实与"把没做的说成做了"**危害相同**：都会让下一个人做错事 ——
以为没做的其实已做好（重复投入），而真正缺的那一项反而没人看见。

**规则**：一个需求项内部只要包含多个可独立验收的子项，
台账就必须**逐子项标注状态**，不用笼统的"部分完成"覆盖。

**一个有用的判据**：标注"未做"前，先证明它**做不到或没做**。
本轮就是按这个判据核对的 —— 核对中发现②③④其实是完成的；
而①也顺带查明了**它为什么做不到**（缺打卡时间这一数据来源，不是缺字段），
这比单写一句"未做"有用得多。

另有 `2026-10-15-upgrade-batch3-asset-accounts.sql` 补 1603/1604 科目与 IMP/DSP 编号规则，

### 4.1.1 退货明细行表：为什么删除而不是实现

`pur_return_item` / `sales_return_item` 原本被记为"缺口：需业务确认是否要行级退货"。
**实测核对后发现它们不是"未实现"，而是"结构上不可能被使用"**：

1. **上游单据没有明细行**：`pur_order` 是一张**扁平单行**表 ——
   `item_name` / `quantity` / `unit_price` / `tax_rate` 全在表头上，
   不存在 `pur_order_item`；`erp_project_revenue`（收入确认单）同理。
   全库唯一的"订单明细"表是 `erp_contract_item`（合同行），与采购/收入无关。
   → **退货行没有可引用的对象**。
2. **退货能力并不依赖它**：部分退货已由 `pur_return.return_quantity`（整数数量）
   + `returnableQuantity()`（可退 = 已验收 − 已退，含校验）完整支持；
   金额按原单税率倒算（`returnAmount()` / `sumReturnLines()`），与行表无关。
3. **零引用**：两张表在 `server/`、`client/`、`shared/`、`scripts/` 中
   除 `schema.ts` 定义外无任何引用（含 raw SQL 表名）。

**处置**：迁移 `2026-10-15-upgrade-batch3z-drop-unusable-return-items.sql`
删除两张表（实测删除前 0 行数据）。理由与要点：

- 保留的代价是 **schema 会说谎** —— 看到这两张表的人会以为系统支持按行退货，
  进而设计依赖它的流程，最后发现上游没有明细行；
- 删除是**可逆**的：若将来真的引入 `pur_order_item`，重建只需一条迁移
  （原定义在 `batch3-core.sql`，且届时"可退数量"基准也应从表头
  `accepted_quantity` 改为行级）；
- 该表原本的注释写的是"承载『按物料行退货』的扩展能力"——
  即**面向未来预留**。预留结构若长期没有落脚点，就是负债而非资产。

### 4.1.2 实测：报表性能（NFR-P2「报表接口 P95 < 3s，10 万凭证行」）

两个脚本，**真实库的结论以第二个为准**：

- `npm run bench:report` —— pglite，零依赖、用于快速回归趋势；
- `node ./scripts/bench-report-query-pg.mjs` —— **真实 PostgreSQL**，
  在隔离 schema（`bench_nfrp2`，结束即 DROP，不触碰 public）中造数、
  `ANALYZE` 后预热采样 20 次，并核对 `EXPLAIN (ANALYZE)` 计划。

**真实 PostgreSQL，10 万凭证行 / 5 万张凭证（P50 / P95）**：

| 查询 | P50 | P95 |
|---|---|---|
| 科目余额表（全年累计到年末） | 166 ms | **292 ms** |
| 科目余额表（年中单月） | 147 ms | 160 ms |
| 本期发生额按科目聚合（利润表） | 32 ms | 45 ms |

`EXPLAIN` 确认 `Bitmap Index Scan on idx_fin_voucher_period_status` →
**NFR-P2 要求的索引确实生效**（不是仅"存在"）。

**结论**：最重的科目余额表 P95 ≈ 292 ms，**3s 预算约 10 倍余量**；
按线性外推，凭证行数到 **约 100 万行**才逼近 1s，**到约 500 万行**才可能破 3s。
因此**暂不实现余额快照物化**。

> ⚠️ **一个被实测纠正的判断**：最初只跑 pglite，得到"约 100ms、3s 预算 30 倍余量"，
> 并据此认为"pglite 慢于真实 PG、所以是保守下界"。
> **真实 PG 复测后并不成立** —— 最重的查询在真实库上是 292ms（P95），
> 余量是 10 倍而非 30 倍。原因：该查询的 `opening` 部分要聚合"当前期间之前的
> **全部历史**"，代价随累计数据量增长，而 pglite 在这个访问模式下反而更快。
>
> 教训：**不同引擎的"相对快慢"依赖具体访问模式，不能靠直觉假设哪个是下界；
> 涉及性能结论必须在目标引擎上复测。** 余量从 30 倍修正为 10 倍仍然达标，
> 但如果只跑 pglite 就写进结论，会把一个偏乐观的数字当成事实。

> 这条记录的价值不在于"性能没问题"，而在于**把"要不要做物化"从猜变成了有数据的决定**。
> 需求书列了 `fin_account_balance_snapshot` 作为设计，但设计假设（实时聚合太慢）
> 在实测下不成立；照搬设计会白增一处"报表可能过期"的风险点。

### 4.2 C-14 ①考勤规则为何无法直接实现

验收标准①是「配置班次后**迟到自动判定**」。实测：

- `hr_attendance` 只有 `id / employee_id / work_date / status / remark`
  —— **完全没有上下班打卡时间字段**；
- 因此 `status='late'`（`HrStatusBadge.tsx` 里硬编码的"迟到"）是**人工选的**，不是算出来的；
- 全仓 `lateMinutes` / `earlyLeave` / `overtime` / `班次` 均 **0 处命中**，也没有排班表。

**"迟到"本质是"实际打卡时间晚于班次上班时间 + 宽限"。** 没有打卡时间、
没有班次定义，就没有可比较的两个值 —— 缺的不是几个字段，而是**数据来源本身**。

**正确的前置顺序（需业务确认后立项）**：
1. 打卡数据来源（考勤机 / 员工自助打卡 / 飞书考勤 API；仓库现有
   `flexible_labor_hours_sync_1` 是**工时**入向，不含考勤）；
2. 排班主数据：班次（上下班时间、跨天班、弹性区间）+ 员工排班 + 节假日日历；
   **不先定这个，"迟到"没有基准**；
3. `hr_attendance` 扩展 `check_in_at` / `check_out_at`（判定迟到/早退/加班的必要前提）；
4. 在 1–3 之上才谈自动判定与加班倍数、月度汇总、工资联动。

需求书给的 C-14 整体 48–72h 隐含"打卡时间已有"的假设；若要连数据来源一起做，
需单独立项（涉及硬件或第三方接口）。

### 4.3 D-08 转交不落归属：需求书点名、但一直未修的缺陷

需求书 D-08 的"现状与差距"原文即写明：**「`ast_change` 存在但 transfer 不落归属」**。
台账曾把 D-08 标为 ✅，本轮核对发现**该问题至今未修**：

- `ast_change` 只有 `before_value` / `after_value` 两个**自由文本**列
  （形如 `状态:在用；部门:研发部；项目:无`）；
- `AssetChangeType` 含 `'transfer'`，但 `changeAction` 的 approve 分支
  **只处理 `receive` 与 `scrap`** —— transfer 审批通过后什么都不发生；
- 结果：转交单显示"已批准"，而 `ast_asset.department_id` / `project_id`
  **一点没变**。资产仍挂原部门，**折旧分摊与部门成本归集就此错位**。

**为什么这类缺陷比"功能缺失"更危险**：**它表现为成功** ——
审批通过、状态变绿、界面无异常。只有等到部门成本对不上时才会被发现，
而那时往往已跨了多个期间，追溯调整成本极高。

**根因**：流转信息只存在自由文本里，没有结构化目标可供审批时写回。

**修复**（迁移 `2026-10-15-upgrade-d08-transfer-ownership.sql`）：
1. `ast_change` 补 `target_department_id` / `target_project_id`（结构化，
   可空 = 本次不改该维度，因此支持"只转部门"或"只转项目"）；
2. 创建变更单时**强制校验**：transfer 必须至少给一个目标
   （否则直接拒绝，而不是让它"看起来成功"）；目标不存在也在创建时拒绝，
   不留到审批阶段才因外键失败（那时单据已进入流程）；
3. 审批通过时**真正写回** `ast_asset.department_id` / `project_id`；
4. `after_value` 文本降级为**展示快照**，不再承担数据传递职责
   —— 文本解析不可靠（部门改名、格式微调都会失效）。

**一个自己踩到的坑**：FK 我一开始写成了 `sys_department`，
但 `AssetService` 的 join 用的是 **`hr_department`**（且 `sys_department` 实测 0 行、
`hr_department` 3 行）。若不核对就落库，非空部门的校验会**全部误拒**。
已修正为 `hr_department`。

**回归测试**（`asset-change-transfer.spec.ts`，8 例）断言落在
**资产归属字段真的变了**，而不是"接口返回成功"：
转交前后归属对比、只转部门、只转项目、驳回不动数据、
缺目标被拒、目标不存在被拒、返回结构化中文名、重复审批被拒。
**实测验证该测试确实能抓到原缺陷**：临时移除写回逻辑后 3 例失败，还原后 8/8 通过。

## 5. 变更过的关键约定（供后续开发对齐）

1. **RBAC 只允许 `@CanCapability` / `@CanCapabilityRead`**，禁止 `@CanRole`（`check:rbac` 会拦）。
   能力码必须先在 `shared/rbac.ts` 的 `Capability` 联合类型中登记。
   ⚠️ `CanCapability` 默认按**写权限**（矩阵中 `rw`）判定；只读接口必须用 `CanCapabilityRead`。
2. **`@Body()` 必须是 class DTO**（`implements` shared 契约类型 + class-validator 装饰器），
   且 **class 必须定义在 controller 类之前** —— 否则生产构建启动会抛
   `Cannot access 'X' before initialization`（TDZ；`tsc --noEmit` 与 jest 都发现不了）。
3. **迁移文件名排序即执行顺序**：新迁移必须排在所依赖的建表迁移之后
   （既有先例：`...-batch1z-code-rules-seed.sql` 的 `z`）。改名前先跑 `npm run migrate:dryrun`。
4. **新增契约类型一律写入 `shared/api.interface.ts`**，`client/src/api/**` 禁止本地 interface/type/内联对象类型。
5. **业务编号**用 `generateBizCode(db, table, col, 'PREFIX', now, { bizType })`，
   前缀与位数由 `sys_code_rule` 配置；财务类单据编号禁止重用。
6. **日期**统一用 `server/common/utils/biz-date.ts`（Asia/Shanghai），月份为 `YYYY-MM` 字符串。
