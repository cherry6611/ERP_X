fix(A-01/A-06): 修复 fin_voucher 缺 tax_entity_id 导致按纳税主体查询全部 500

## 这是一个 P0 真实 bug（实测复现）

`ledgers.service.ts` / `reports.service.ts` / `vat-declaration.service.ts` /
`aux-combination.service.ts` 的 SQL 都写了
`AND v.tax_entity_id = ${taxEntityId}::uuid`，
但 **`fin_voucher` 从来没有这一列**。实测确认：

```
❌ SELECT 1 FROM fin_voucher v WHERE v.tax_entity_id IS NOT NULL
   → column v.tax_entity_id does not exist
```

后果：**任何传了 `taxEntityId` 的请求直接 500**。受影响范围包括
A-01 资产负债表、A-02 利润表/现金流量表、A-03 全部账簿、A-06 增值税底稿、D-03 辅助核算组合
—— 也就是需求书明确要求的「支持按纳税主体分别出具」。

## 为什么长期没被 CI 拦住（值得记录）

`migrate:dryrun` 与迁移链集成测试**只执行 DDL，从不执行这些业务查询**；
而现有集成测试都没有传 `taxEntityId`。所以"迁移通过"与"功能可用"之间
存在一条完全没被覆盖的缝。这正是台账里"迁移建了表 ≠ 功能完成"教训的同一类问题，
只是这次连表都没建全。

## 修复内容

**迁移 `2026-10-15-upgrade-batch1z-voucher-tax-entity.sql`**：
- 补 `fin_voucher.tax_entity_id` + 外键（`ON DELETE SET NULL`）+ 复合索引；
- **回填**：优先按 `source_ref` 命中 `erp_contract` 取合同主体，
  其次在「系统恰有一个启用中的默认主体」时兜底；
- 新增自检视图 `v_fin_voucher_unassigned_entity`：按期间列出**未归属**凭证。
  为什么必须显式暴露：未归属凭证不计入任何主体报表，是个**静默缺口**，
  没有这个视图就没人知道报表少了一块。

多主体下**刻意不做**默认主体兜底 —— 硬塞会让该主体报表虚增。
**一个看起来正确的错误数字，比一个明显的缺口更危险。**

**写入侧**：`VoucherService` 新增 `resolveTaxEntityId()`，
优先级为「请求显式指定 → `sourceRef` 命中合同 → 唯一默认主体」。
`CreateVoucherDto` 增加可选 `taxEntityId`（契约 append-only）。

## 顺带修复同类 bug：`ast_asset.keeper_employee_id`

用同一次审计发现 `/api/asset/assets/:id/ownership` 也引用不存在的列并会 500。
`ast_asset` 实际没有保管人字段，因此**不臆造**这个列（保管/领用/离职移交
是一个真实业务模型，不是加个 nullable 列就能成立），
改为如实返回 `keeperName: null` 并在注释里写明未实现的原因。契约字段保留以免破坏接口形状。

## 遇到过并修正的三个问题（都是我自己引入的）

1. **`is_default = true` 写成 boolean**：该列是 `integer` 标志位（`0/1`），
   pglite 报 `operator does not exist: integer = boolean`；
2. **`VoucherSourceType` 没有 `'contract'`**：我原以为凭证来源类型含合同，
   实际取值是 `receipt/payment/expense/payroll/depreciation/invoice/manual`
   —— 合同不是凭证的直接来源。改为只按 `sourceRef` 命中合同，与来源类型无关；
3. **把解析放进 `db.transaction` 导致 pglite 死锁**：单条测试 5s 超时、
   整个 `accounting-chain` 套件（12 例）挂起 130s+ 不结束。
   移到**事务外**即恢复（7s 通过）。修好后我记录了原因：
   查多张表的推导逻辑不该占用写事务，与 AGENTS.md「外部 IO 必须在事务外」同源。

## 新增回归测试 `column-reference-audit.spec.ts`（5 例）

把这类 bug 变成 CI 可发现：

1. **静态审计**：扫描 `server` 下全部 `.ts` 源码，建立「SQL 别名 → 表」映射，
   与真实库结构比对，任何不存在的列即失败；
2. **行为验证**：在迁移后的库上真的插入两个纳税主体 + 各一张凭证，
   执行按主体过滤的余额查询，断言**隔离正确**（100 / 700，不过滤时 800）
   —— 同时排除"恰好都返回同一个数"的假通过；
3. 未归属凭证必须出现在自检视图中（不能悄悄消失）。

**验证了这个测试真会失败**：临时插入 `a.ghost_employee_id` 后立刻报
`ast_asset 没有列 ghost_employee_id`；还原后 5/5 通过。
