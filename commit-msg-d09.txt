feat(D-09): 审计日志防篡改（只追加约束 + 校验和链）—— NFR-S8

## 问题

NFR-S8 要求「审计日志不可篡改（追加写 + 校验和 + 归档）」，而 `comp_audit_log`
当时**可以被任意 UPDATE**（表上没有任何只追加约束），也没有校验和 ——
因此"日志被改过"这件事本身无法被发现，等保测评会直接列为不符合项。

## 实现

`2026-10-15-upgrade-d09-audit-immutability.sql`：

1. **链式校验和**：新增 `chain_seq` / `prev_hash` / `chain_hash` 三列，
   `chain_hash = md5(prev_hash|seq|actor|action|object_type|object_id|object_code|创建时间|detail)`，
   历史 303 行按插入顺序回填。
   `trg_comp_audit_log_chain` 在 INSERT 时自动串链，并用
   `pg_advisory_xact_lock(hashtext('comp_audit_log_chain'))` 串行化
   「读上一行 hash → 写入」——**不加锁会让并发插入读到同一个 prev_hash，
   链分叉且校验必然失败**，这是该设计最容易漏掉的一点。
2. **只追加约束**：`trg_comp_audit_log_immutable` 拒绝所有 UPDATE
   （可读中文 + `ERRCODE = restrict_violation`）。
3. **DELETE 的唯一例外**：归档清理。`retention.service.ts` 的语义是
   「先复制进 `comp_audit_log_archive` 再删在线行」= 移出在线表而非销毁；
   直接封死 DELETE 会让归档功能失效。因此允许 DELETE **仅当**会话内显式设置
   `app.retention_purge = 'on'`（`SET LOCAL`，不泄漏到事务外）。
   留例外的代价是"清理动作本身必须显式"，这恰好符合内控：谁在什么时候清理了
   审计日志，是一次有意为之的操作，而不是某段业务代码顺手删掉。
4. 归档表同步记录 `source_chain_hash` / `source_chain_seq`，便于事后比对。

配套：
- `AuditChainService`：在线校验（逐行重算 + 链关系 + 链根是否在归档表中）、
  锚点导出、只追加自检；3 条新接口
- 前端「审计日志」页新增校验面板（校验链 / 只追加自检 / 导出锚点）
- `scripts/check-audit-immutability.mjs` + `npm run check:audit-immutability`：
  **真实 PostgreSQL** 上的 10 项行为自检；CI 在配置 `DATABASE_URL` 时执行，
  未配置时打 `::warning::` 跳过（不静默通过）
- `docs/D09-compliance-hardening.md`：已落地范围、验证方式、**以及仍未做的部分**

## 一个值得记录的验证陷阱

自检脚本第一版第 ⑨ 项误报"`SET LOCAL` 泄漏"。真实原因是第 ⑧ 项已把探针行删掉，
第 ⑨ 项的 `DELETE ... WHERE actor='d09-probe'` 影响 **0 行**，而触发器是
`FOR EACH ROW` —— **0 行即不触发**，"没有报错"被误读为"允许删除"。
教训：验证"约束会拒绝"时必须**先确认待操作的行确实存在**，
否则断言的是一个永远为真的空操作。已修正并在脚本注释中记录。
