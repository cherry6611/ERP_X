# D-04 决策评估：合并报表（多纳税主体合并与抵消）

> 需求书 D-04：「**合并报表**（多纳税主体 / 多法人合并抵消）」，P3，60–90 h，
> 备注：**「组织规模扩大后才需要」**。
>
> 本文是**评估与设计**，不是实现。逐项核对了前置数据是否具备，
> 结论见第 4 节 —— **其中一项前置缺失，需先决策**。

## 1. 结论摘要

| 项 | 现状 | 能否直接做 |
|---|---|---|
| 多主体**分别**出具报表 | ✅ 已具备（`taxEntityId` 过滤，实测一致） | — |
| 多主体**简单相加**（汇总） | ✅ 结构上可行 | 可做 |
| 内部往来**抵消**：应收/应付（客户侧） | ⚠️ 可识别（USCC 匹配） | 可做 |
| 内部往来**抵消**：应收/应付（供应商侧） | ❌ **缺识别字段** | **需先补数据** |
| 内部收入/成本抵消 | ❌ 同上，依赖供应商侧识别 | 部分可做 |
| 外币折算 | ❌ 无多币种字段 | 需求书未要求，暂不涉及 |

**一句话**：合并报表的**骨架**（汇总 + 客户侧抵消）可以立即做；
但**供应商侧的内部往来无法识别**，因此抵消会**不完整** ——
而不完整的抵消会给出"合并后仍有内部往来余额"的错误数字，
比不做合并更危险（看起来像已抵消）。

## 2. 已具备的前置（实测）

### 2.1 多主体分别出具 —— 已完成

- `fin_voucher.tax_entity_id` 已存在（本轮之前已修复其缺失导致的 500）；
- `ReportsService.balanceSheet({ taxEntityId })` / `incomeStatement` /
  `LedgersService` / `VatDeclarationService` 均支持按主体过滤。

**实测一致性**（2026-10-15）：

```
不按主体过滤：8 个科目，借贷净额合计 0.00
CS001               : 0 科目，净额 0.00
TE-2026-10-13212157 : 8 科目，净额 0.00
逐主体求和 = 0.00  全量 = 0.00  → ✅ 一致
未归属主体的有效凭证：0 张
```

即：**主体报表之和 = 全量报表**，没有"漏在主体之外"的凭证。
这是合并报表的第一步，且已经成立。

### 2.2 关联方识别 —— 客户侧可行，供应商侧不可行

内部往来的抵消前提是**知道哪些往来是"内部"的**。实测字段：

| 表 | USCC（统一社会信用代码） | 能否与集团主体匹配 |
|---|---|---|
| `md_tax_entity`（集团主体） | ✅ 有 `uscc` | — |
| `md_customer`（客户） | ✅ 有 `uscc` | ✅ **可以** |
| `md_supplier`（供应商） | ❌ **没有** | ❌ **不能** |

因此：

- **客户侧**（应收账款 `erp_ar` + 收入 `erp_project_revenue`）：
  可用 `md_customer.uscc = md_tax_entity.uscc` 识别"客户就是集团内另一主体"，
  从而找出内部应收与内部收入 → **可抵消**；
- **供应商侧**（应付 `erp_ap_bill` + 成本 `erp_project_cost`）：
  `md_supplier` **没有 uscc**，无法判断某供应商是不是集团内主体
  → **内部应付与内部成本无法识别 → 无法抵消**。

> ⚠️ `md_supplier.tax_entity_id` **不是**"供应商所属主体"，而是
> "该供应商关联到我方哪个纳税主体"（我方口径），不能用于判断供应商是否关联方。
> 这一点容易误用，特此写明。

## 3. 设计方案（若决定实施）

### 3.1 汇总层

```
合并 = Σ(各主体报表) − 抵消分录
```

不新建表：`ReportsService` 已有按主体出具能力，合并层只需
对所选主体逐个取数再相加。**关键约束**：主体必须**互斥且完整**，
否则会重复计算或遗漏 —— 因此合并请求应显式传入主体清单，
而不是"全部主体"（`tax_entity_id IS NULL` 的未归属凭证必须单独提示，
不能被悄悄算进某一主体）。

### 3.2 抵消层（纯函数 + 数据取数分离）

抵消是**规则**而非取数，适合做成纯函数（与 D-03/D-05/D-06 同一模式）：

| 抵消项 | 借方 | 贷方 | 依据 |
|---|---|---|---|
| 内部应收/应付 | 应付账款 2202 | 应收账款 1122 | 客户=集团主体的 `erp_ar` 余额 |
| 内部收入/成本 | 主营业务收入 6001 | 主营业务成本 6401 | 同上合同下的收入与成本 |

**必须给出的两个诚实信号**：

1. **抵消不完整度**：供应商侧无法识别 → 合并报表必须显式标注
   "内部应付/成本未抵消（缺供应商关联方标识）"，而不是给出一份
   "看起来已完全抵消"的报表；
2. **单边差异**：内部应收与内部应付若不相等（常见于在途、时间性差异），
   必须列出差额与原因，不能强行轧平 —— 强行轧平会掩盖真实的账务错误。

### 3.3 需先补的前置（若要完整抵消）

给 `md_supplier` 增加 `uscc`（或 `is_related_party` 标记 + 所属主体 id），
并在供应商维护界面补录。这是一次**主数据补录工作**，
不是纯开发 —— 需要业务方提供集团内供应商清单。

## 4. 建议

**本阶段不做**，理由与需求书自己的备注一致（"组织规模扩大后才需要"）：

1. **实测只有 1 个主体有凭证**（CS001 0 张、TE-… 12 张），
   合并与不合并的结果**完全相同** —— 现在做，无法验证正确性，
   只会得到一份"抵消前后一样"的报表。
   且抵消对象本身数据极少：`erp_ar` 4 条、`erp_ap_bill` 4 条、
   `md_customer` 5 条（仅 **1** 条填了 uscc）、`md_supplier` 4 条（无 uscc）。
   **在只有个位数单据上做合并报表，等于没有验证。**
2. **供应商侧前置缺失**，完整抵消做不到；而不完整的抵消会给出
   错误数字（见 §3.2），风险大于收益；
3. 客户侧抵消虽可做，但**只有单侧抵消**的合并报表在会计上没有意义
   （内部交易必然双边，只抵消一边会让合并报表出现虚构的"对外应收"）。

**重新评估的触发条件**（任一满足即应实施）：

- 第二个主体开始有实际凭证（届时合并才可被验证）；
- 组织明确要出**集团合并报表**（对外报送或股东要求）；
- 集团内**供应商**开始与我方主体发生关联交易（届时须先补 `md_supplier.uscc`）。

**若业务现在就需要**，请确认两件事后我再实施：
① 是否接受"供应商侧暂不抵消"并在报表上显式标注；
② 集团内供应商清单能否先补齐 `uscc`。

## 5. 与 D-01/D-10 的关系

- **D-01 门户**（外部账号体系）与 D-04 无依赖；
- **D-10 多租户**（多组织隔离）与 D-04 的"多主体合并"是**两个不同概念**：
  D-10 讲的是把不同公司数据**隔离开**，D-04 讲的是把同一集团内主体数据
  **合起来**。两者若同时做，必须先把"主体"与"租户"的边界定义清楚，
  否则会出现"合并时把别的租户也算进来"这类严重问题。**建议 D-10 先于 D-04**。
